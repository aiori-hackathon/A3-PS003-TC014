# 3. OUR COMPLETE PROJECT IDEA

Traffic conditions differ across locations.

For example:
- Central urban roads may experience consistently high traffic.
- Residential areas may experience lower average traffic.
- Highways may experience different traffic patterns.
- Accidents, diversions, festivals and unusual traffic surges can cause sudden changes.

A centralized traffic-prediction system requires data from multiple locations to be transmitted to a central server.

Federated learning provides an alternative.

Each simulated client trains locally using its own traffic observations. Only model updates are transmitted to the central server.

The central server aggregates these updates and distributes the improved global model.

However, conventional federated learning can still produce considerable communication overhead because clients repeatedly upload model updates and download global models.

Our proposed system aims to improve this process.

### Our central contribution

Develop an intelligent, communication-budget-aware federated aggregation framework that:

1. Predicts traffic flow using a spatial-temporal model.
2. Allows local training at multiple simulated clients.
3. Aggregates model updates using a correct FedAvg foundation.
4. Identifies clients that need to communicate based on meaningful traffic changes.
5. Avoids unnecessary communication when local traffic conditions remain stable.
6. Operates within a configurable communication budget.
7. Uses lightweight update validation and optional update compression.
8. Measures the accuracy-versus-communication trade-off.

The objective is not merely to reduce the number of communication rounds.

The objective is to achieve a better balance between:

- Prediction accuracy.
- Total communication bytes.
- Convergence speed.
- Computational requirements.
- Robustness of model updates.

A solution that reduces communication but significantly damages prediction accuracy must not be considered successful.

# 6. FEDERATED LEARNING – STANDARD BASELINE

Implement conventional Federated Averaging (FedAvg) before developing our proposed improvements.

### Working architecture

Five virtual clients:

Client 1
Client 2
Client 3
Client 4
Client 5

Central aggregation server.

Each round must follow this sequence:

1. Server distributes the current global model to participating clients.
2. Each client initializes or updates its local model using the received global parameters.
3. Each client trains locally using its own training data.
4. Each client sends its updated model parameters to the server.
5. Server validates update compatibility.
6. Server aggregates client parameters.
7. Server creates the new global model.
8. Server distributes the new global model in the next communication round.

### FedAvg mathematical requirement

Use sample-count-weighted aggregation:

W_global = Σ (n_i / Σ n_j) × W_i

Where:
- W_i = model parameters from client i.
- n_i = number of local training samples at client i.
- W_global = aggregated global parameters.

Implement the aggregation carefully.

Do not simply average model parameters without considering local sample counts.

Ensure that:
- All participating models have compatible parameter names and shapes.
- Aggregation uses the correct data types.
- No NaN or infinite values enter the global model.
- The aggregated parameters are correctly loaded into the global model.

### Essential FedAvg tests

Create unit tests for:
- Two-client aggregation.
- Five-client aggregation.
- Unequal sample counts.
- Identical client updates.
- Known numerical examples.
- Invalid tensor dimensions.
- Non-finite values.
- Correct global-model redistribution.

Test the aggregation mathematically using small known tensors before running expensive training.

### Federated baseline experiments

Evaluate:
1. IID client distribution.
2. Non-IID client distribution.

Use the same STGCN architecture and forecasting configuration as the centralized baseline.

Record:
- MAE.
- RMSE.
- Communication bytes.
- Number of communication rounds.
- Convergence behaviour.
- Training time.

This standard FedAvg implementation is our reference for evaluating every proposed improvement.

# 7. MOST IMPORTANT COMPONENT – PROPOSED AGGREGATION AND COMMUNICATION OPTIMIZATION

This is the central research contribution of our project.

Do not treat aggregation as a small final function.

Give this component the highest technical priority after the dataset and baseline model are validated.

Our goal is to improve communication efficiency without sacrificing useful learning information.

Develop a proposed V2 framework on top of standard FedAvg.

Call the proposed approach:

**Budget-Aware Event-Triggered Federated Aggregation (BEFA).**

This is our proposed framework name. Do not claim it is an established published algorithm.

### A. Event-aware client participation

Conventional federated learning can communicate at every scheduled round, even when local traffic conditions have changed very little.

Develop an event-aware participation mechanism.

Each client should monitor a configurable local traffic-change score.

The score may consider:
- Difference between recent and previous traffic observations.
- Relative traffic-flow change.
- Local prediction error or validation deterioration.
- Significant deviations from the client's recent traffic pattern.

A client should request participation when its local conditions indicate that a new update may be useful.

Avoid triggering communication for insignificant fluctuations.

However, do not allow a client to remain excluded indefinitely.

Introduce a maximum communication interval.

Also introduce a fallback mechanism for important clients or significant prediction deterioration.

Document the exact event score, thresholds and selection logic.

Tune thresholds using training or validation data only, never the test set.

### B. Hard communication budget

Implement a configurable communication budget.

Track actual serialized communication rather than estimating bytes from model parameter counts alone.

Measure:

1. Global-model download bytes.
2. Local-update upload bytes.
3. Total bytes per round.
4. Cumulative communication bytes.
5. Remaining budget.
6. Deferred updates.
7. Number of participating clients.

Use actual serialized payload sizes or an equivalent reproducible transport simulation.

Clearly define whether protocol overhead is included.

Before sending an update, check whether the remaining budget can accommodate the exchange.

If it cannot:
- Do not silently exceed the budget.
- Defer or reject the exchange according to the scheduling policy.
- Log the decision.
- Preserve the latest accepted global model.
- Allow future participation when the budget policy permits.

Budget enforcement must be tested with known payload sizes.

### C. Intelligent aggregation

Standard sample-weighted FedAvg must remain our baseline.

For the proposed version, investigate whether the aggregation process can improve update usefulness without introducing arbitrary weights.

Possible factors to investigate:

- Local sample count.
- Update freshness.
- Update validity.
- Local validation performance.
- Client traffic-change significance.

Do not combine these into an arbitrary formula.

Develop a mathematically justified weighting or selection strategy.

First implement the simplest valid approach.

Then evaluate whether a validation-informed or event-informed aggregation weight adds measurable value over standard FedAvg.

Avoid allowing a single client's local validation score to dominate global learning.

Compare proposed aggregation against standard FedAvg under IID and non-IID conditions.

Document the formula and its assumptions.

### D. Update compression – optional advancement

Investigate lightweight quantization of model updates to reduce upload bytes.

A possible implementation is 8-bit quantization.

If used:
- Measure actual serialized payload size.
- Dequantize correctly at the server.
- Compare prediction accuracy before and after compression.
- Test numerical stability.
- Consider error-feedback compensation if quantization errors accumulate.
- Include compression overhead in byte accounting.

Do not enable compression automatically until the uncompressed baseline works.

Treat compression as an experimental enhancement, not a mandatory dependency.

### E. Lightweight update security and robustness

Implement basic checks:
- Correct parameter names and shapes.
- Finite tensor values.
- Stale update detection.
- Duplicate update detection.
- Configurable update norm clipping.
- Rejection logging.

Do not claim complete Byzantine fault tolerance, differential privacy or formal security.

These are lightweight safeguards for the prototype.

### F. Resource optimization

Release temporary client training resources after aggregation when they are no longer required.

Consider:
- Temporary local models.
- Gradients.
- Unnecessary optimizer resources.
- Temporary serialized payloads.

Preserve the global model and any client state required by the experiment.

If optimizer state is reset between rounds, document and evaluate the effect on convergence.

Do not confuse RAM reduction with communication reduction.

### G. Final proposed aggregation workflow

The proposed system should operate as follows:

1. Server maintains the current global STGCN model.
2. Clients receive the current global model when scheduled.
3. Clients monitor local traffic conditions.
4. Event-aware logic determines whether an update is useful.
5. The budget manager checks available communication capacity.
6. Selected clients perform local training.
7. Updates are optionally compressed.
8. Server validates freshness, shapes and numerical values.
9. Invalid or duplicate updates are rejected.
10. Accepted updates are aggregated using the proposed aggregation strategy.
11. The new global model is produced.
12. Communication statistics are recorded.
13. Temporary resources are released.
14. The process continues until the training or budget stopping condition is reached.

The aggregation must remain mathematically correct and reproducible.

### H. Critical success condition

Our V2 is successful only if experiments demonstrate a meaningful improvement in communication efficiency while maintaining or improving predictive performance relative to standard FedAvg.

If accuracy decreases, report the trade-off honestly.

Do not claim that a method improves both metrics unless the experimental results support it.
